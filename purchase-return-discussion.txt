  5. Stock reserve/hold — saya setuju tambah reservation quantity

  Saya setuju dengan pendekatan reservation/hold quantity di inventory layer.
  Untuk Purchase Return yang belum confirmed, barang sebaiknya dianggap tidak 
  available untuk outbound lain.

  Secara konsep:

  onHandQty = quantity fisik ada
  reservedQty = quantity sudah di-hold untuk dokumen outbound belum completed
  availableQty = onHandQty - reservedQty

  Lalu GI / Stock Adjustment / Delivery Order nantinya harus memakai
  availableQty, bukan hanya onHandQty.

  Untuk serialized item

  Catatan kamu benar: barang serial tidak boleh reserve sebagian secara abstrak.

  Untuk serialized item, reservation harus by serial number:

  Product 1, Container 1:
  - Serial A001 → reserved by PR-001
  - Serial A002 → free
  - Serial A003 → free

  Bukan:

  Product 1, Container 1, qty 5, reserved 2

  Karena “reserved 2” tidak menjawab serial mana yang di-hold.

  Jadi saya pikir desain reservation-nya perlu dua level:

  A. Non-serialized reservation

  InventoryReservation
  - productId
  - containerId
  - quantityReserved
  - sourceType = PURCHASE_RETURN
  - sourceId = purchaseReturnId
  - sourceLineId = purchaseReturnLineId
  - valuationRefType = GOODS_RECEIPT
  - valuationRefId = grId
  - valuationRefLineId = grLineId
  - status = ACTIVE / RELEASED / CONSUMED

  B. Serialized reservation

  InventoryReservation
  - productId
  - containerId
  - serialNumber
  - quantityReserved = 1
  - sourceType = PURCHASE_RETURN
  - sourceId = purchaseReturnId
  - sourceLineId = purchaseReturnLineId
  - valuationRef...
  - status = ACTIVE / RELEASED / CONSUMED

  Domain rule:
  - Jika product serialized:
    - quantityReserved harus 1 per reservation row
    - serialNumber wajib
    - base qty harus bilangan bulat
    - jumlah serial selected harus sama dengan qty return
  - Jika non-serialized:
    - serialNumber harus null
    - quantity boleh decimal sesuai UOM/base UOM policy

  6. Returnable qty harus memperhitungkan barang yang sudah keluar

  Betul, formula saya sebelumnya belum lengkap kalau ada Sales/GI outbound lain.
  Formula yang lebih benar:

  returnableQty(grLine)
  =
  min(
    grLine.receivedBaseQty
      - completedReturnedBaseQtyFromThisGrLine
      - pendingReturnReservedBaseQtyFromThisGrLine,

    remainingSpecificLayerQty(grLine)
      - activeNonReturnReservationsAgainstThisLayer
  )

  Atau versi bisnisnya:

  returnable = barang dari GR line ini yang:
  1. pernah diterima
  2. belum pernah di-return confirmed
  3. belum sedang di-hold oleh PR lain
  4. masih benar-benar available/on-hand
  5. masih berada pada valuation layer asal yang sama

  Ini menjawab kasus:

  ▎ PO → GR 10 pcs, lalu 3 pcs sudah dijual/keluar lewat Sales Delivery.

  Maka secara valuation layer:
  - GR line awal: 10
  - sudah consumed outbound lain: 3
  - remaining layer: 7
  - returnable max: 7, bukan 10

  Jadi source of truth terpenting untuk non-serial adalah 
  ValuationLayer.remainingQuantity dari GR line asal, bukan cuma GR quantity.

  Untuk serial item

  Lebih mudah:
  - serial yang sudah keluar tidak ada di on-hand / layer aktif
  - hanya serial yang masih available di container yang bisa dipilih
  - serial yang sudah reserved oleh PR lain juga tidak bisa dipilih

  Untuk non-serial item: FIFO atau referensi GR?

  Untuk Purchase Return, saya tetap rekomendasikan bukan FIFO umum, tapi
  specific GR valuation layer.

  Karena return ke supplier secara akuntansi adalah reversal dari penerimaan
  tertentu. Kalau sistem pakai FIFO umum, bisa terjadi salah nilai.

  Contoh:

  GR-001: 10 pcs @ 100.000
  GR-002: 10 pcs @ 120.000

  User return barang dari GR-002 sebanyak 2 pcs.

  Kalau FIFO umum, sistem bisa consume GR-001 @100.000, padahal return yang
  dipilih berasal dari GR-002 @120.000. Ini menyebabkan inventory dan
  clearing/AP reversal salah.

  Jadi untuk Purchase Return:

  GI line valuationRefType = GOODS_RECEIPT
  GI line valuationRefId = grId
  GI line valuationRefLineId = grLineId

  Kemudian StockService.adjust(ISSUE) harus consume layer yang match dengan
  valuation ref tersebut. Dari GI core, field ini sudah disiapkan dan dipassing
  ke stock payload.

  ---
  Catatan Journal: harga return disamakan dengan PO atau GR?

  Ini perlu diluruskan sedikit.

  Dari diskusi GI core, yang paling aman bukan sekadar “sama dengan PO”, tetapi:

  ▎ Inventory value return harus mengikuti nilai layer GR asal.

  Dalam sistem saat ini, GR valuation kemungkinan mengambil harga dari PO +
  exchange rate PO/GR snapshot. Jadi secara praktis nilainya sering sama dengan
  PO. Tapi istilah yang lebih akurat adalah:

  Purchase Return memakai cost/value dari Goods Receipt / valuation layer asal.

  Bukan harga return baru.

  Kenapa bukan harga baru di Purchase Return?

  Karena Purchase Return adalah reversal fisik atas barang yang sudah masuk
  inventory. Kalau barang masuk dengan nilai buku Rp100.000, lalu keluar untuk
  return juga harus mengurangi inventory Rp100.000. Kalau return pakai harga
  lain, inventory valuation bisa mismatch.

  ---
  Bagaimana ERP profesional menangani perbedaan harga atau currency rate?

  Biasanya tergantung timing dan dokumen AP-nya.

  Case A — Return sebelum Vendor Bill

  Flow:

  PO → GR → Purchase Return
  Vendor Bill belum dibuat/dipost

  Accounting umum:

  Saat GR:
  DR Inventory
     CR GR/IR Clearing

  Saat Return:
  DR GR/IR Clearing
     CR Inventory

  Nilai return biasanya mengikuti nilai GR/PO receipt. Tidak ada FX gain/loss
  karena belum ada liability invoice final. Ini murni membalik GR/IR.

  Case B — Return setelah Vendor Bill dipost

  Flow:

  PO → GR → Vendor Bill Posted → Purchase Return → Debit Memo

  Accounting-nya biasanya:

  Saat GR:
  DR Inventory
     CR GR/IR Clearing

  Saat Vendor Bill:
  DR GR/IR Clearing
  DR Input VAT
  DR/CR FX Variance jika ada
     CR Accounts Payable

  Saat Purchase Return:
  DR Purchase Return Clearing / AP Adjustment / Debit Memo Receivable
     CR Inventory
     CR Input VAT Reversal (jika pajak ikut dibalik)

  Lalu Debit Memo memotong AP:

  DR Accounts Payable
     CR Purchase Return Clearing / Debit Memo

  Atau dalam implementasi yang lebih sederhana, saat PR confirmed bisa langsung:

  DR Accounts Payable
     CR Inventory
     CR Input VAT

  Tapi secara profesional biasanya Debit Memo/Credit Note dari vendor menjadi
  dokumen finansial yang memotong AP, terutama kalau Vendor Bill sudah posted.

  Perbedaan currency rate

  Misalnya:

  PO/GR: USD 1 @ 15.000
  Vendor Bill: USD 1 @ 15.300
  Return date: USD 1 @ 15.500

  Untuk inventory:
  - inventory keluar tetap berdasarkan cost layer: Rp15.000

  Untuk AP/debit memo:
  - tergantung kebijakan accounting:
    a. Debit memo memakai original bill rate
    b. Debit memo memakai return date rate
    c. Selisih masuk FX gain/loss

  Namun untuk MVP dan agar tidak kacau:
  - Purchase Return inventory side pakai GR layer/original rate
  - Debit Memo nanti bisa diputuskan apakah:
    - pakai Vendor Bill rate agar memotong AP secara natural, atau
    - pakai GR rate sebagai pure reversal
  - FX variance kalau ada sebaiknya ditangani di Debit Memo, bukan di GI.

  Jadi saya sarankan boundary-nya:

  Purchase Return + GI:
  - Fokus fisik dan inventory valuation.
  - Pakai GR layer cost.
  - Tidak hitung FX variance.

  Debit Memo:
  - Fokus AP adjustment.
  - Menentukan pemotongan AP, pajak, dan FX treatment.

  ---
  Rancangan sementara lifecycle dengan reservation

  Saya propose:

  DRAFT
    - editable
    - belum reserve
    - returnable qty dihitung dari available layer saat form dibuka/save

  SUBMITTED
    - create ApprovalRequest
    - create inventory reservation
    - tidak editable kecuali cancel/reject path

  APPROVED
    - reservation tetap aktif
    - siap confirm

  REJECTED
    - reservation released
    - tidak bisa confirm
    - qty kembali returnable

  CONFIRMED
    - auto create GI from Purchase Return
    - GI complete consume reservation / consume specific GR layer
    - reservation marked CONSUMED
    - Purchase Return locked

  Open question kecil: apakah APPROVED → CONFIRMED dilakukan oleh user
  procurement/accounting, atau warehouse? Karena confirm akan benar-benar
  mengeluarkan stock via GI.
